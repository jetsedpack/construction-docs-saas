# Реализация: критический путь, критерии и реальные зависимости

Оценки — **ориентиры по трудозатратам** для 1 full-stack/python разработчика + часть времени инженера ПТО/эксперта и GPUGO специалиста; **не обещание даты сдачи**. При отсутствии доменного эксперта этапы не должны считаться принятыми.

## W0: 3–5 рабочих дней — постановка границ
Owner продукта, отраслевой эксперт ПТО, GPUGO infra: согласовать Windows-only, владельца данных, право на тестовый корпус, юридические ограничения, точную модель GPU, доступ к тестовому inference endpoint, список 1–2 классов документов. Критерий: signed scope/acceptance checklist.

## W1: ~1–2 недели — исследование и gold dataset
Разметить минимум 30–50 документов нескольких типов и 20+ несоответствий из обезличенных примеров; схемы полей для АОСР, реестра, ПНР, журнала и сертификатов; ответственные за проверку. Критерий: разработчик способен восстановить путь каждой проверки до источника.

## W2: ~2–3 недели — Windows local PoC
UI PySide6, importer PDF/DOCX/XLSX, encrypted vault DPAPI, Rule Engine, issue/review и экспорт **несертифицированного** отчёта по находкам. Критерий: локальные тесты + работа на чистой Windows VM + offline mode.

## W3: ~2 недели — safe gateway
Жёсткий DTO, явное разрешение AI-подсказки, signed/short-lived token broker, клиентские лимиты, API validation, redaction tests, без сохранения prompt на GPUgo. Критерий: packet capture + adversarial tests + ответ GPUGO без привилегий на БД клиента.

## W4: ~2–3 недели — GPUgo inference + оценка
Поднять модель по выбранной лицензии, настроить ingress/auth, тест TP 1/2/4 vs DP, токены/латентности, метрики, SLO; quality benchmark с экспертом. Критерий: выбранная конфигурация зафиксирована, ответы со ссылкой на конкретные issue IDs, fallback offline.

## W5: ~3–5 недель — вертикальная цепочка «одна работа → комплект»
Связать РД → спецификацию → материал → факт → АОСР → исполнительную схему → реестр → журнал; проверить изменения и статус. Критерий: проверяемость руками, файл не редактируется AI, согласованная human workflow.

## W6: ~3–6 недель — enterprise pilot readiness
Роли, аудит, бэкапы, безопасная установка/подпись, отчёт по threat model, конфликты версий, договоры обработки, специфичный нормативный справочник, инструкции эксплуатации. Для нескольких ПТО — спроектировать защищённый **сервер заказчика**, а не расшаривать файл SQLite по сети.

## Дальше
OCR локально, поиск с цитатами, нормоконтроль по редакциям, интеграция ERP/BIM/ЭДО, ЭП, групповая работа и репликация по разрешению. Нельзя обещать, что «один человек заменит десять», пока замер не показал сокращение затрат на единицу корректной ИД.

## Кто нужен
- Продукт: приоритизация сценария, требования, метрики, acceptance.
- Инженер ПТО/электромонтаж/ПНР: определение источников истины, маркировок, исключений и подписантов.
- Python desktop/infra разработчик: importer, vault, UI, gateway, CI.
- GPUGO infra+ML: inference deployment, access control, тестирование качества/нагрузки, эксплуатация.
- Security/legal: модель угроз, разрешённый режим обработки и нормативы.

## Риски на критическом пути
1. Некачественная/неструктурированная РД; одни PDF не восстанавливают факты выполнения.
2. Невозможность формально выделить PII/IP из специфичной маркировки.
3. Лицензии и полный актуальный массив НПА/НТД — отдельный проект, не «скачать всё».
4. ПНР конфигурационные архивы и результаты измерений могут быть особо чувствительными.
5. UI и формат документов часто индивидуальны под заказчика; нужен один пилотный формат, не универсальный генератор.
6. Windows DPAPI ключи и резервное копирование пока не решают enterprise эксплуатацию.
7. 4×6000D не гарантируют поддержку всех моделей без GPU benchmark и актуальных драйверов.

## Метрики
Time to first reviewed ID document; median minutes/doc; false positive rate; recall of seeded issues; % findings with page/cell evidence; % output human-approved; % outbound DTO policy violations (цель 0); latency p95; downtime fallback.
