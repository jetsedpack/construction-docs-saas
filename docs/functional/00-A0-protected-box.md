# A0 — функциональная модель «коробки», согласованная по вопросам 1–3

Состояние: **уточнение требований владельцем продукта 18.11.2026**. Это основа новой A0 и исходные условия для повторного проектирования F01–F07. Не путать с уже реализованным Windows PoC.

## Главное отличие от прежней архитектуры

**«Коробка» уже существует** до загрузки нового объекта. Она содержит правила составления ИД, формы, шаблоны и табличную модель. При поступлении нового пакета она не создаётся заново. В неё добавляются исходники в отдельное изолированное хранилище, а ИИ после анализа приводит рабочую промежуточную версию к существующей структуре и правилам.

**Не**: исходники → GPUGO → создать коробку.

**Да**: исходники → защищённый аппендикс коробки → шлюз → GPUGO → шлюз → промежуточная версия внутри коробки → формирование финального комплекта → проверка и утверждение ПТО.

Две редактируемые схемы draw.io в [A0, 2 страницы](../../diagrams/10-A0-protected-box-functional.drawio) — первая по подсистемам и данным, вторая по процессу.

## Состав «коробки»

| Подсистема | Содержание | Что может сделать ИИ | Кто видит закрытые данные |
| --- | --- | --- | --- |
| A. Защищённый аппендикс | Исходные РД, ТЗ, ТУ, сметы, акты, сертификаты, ПНР, версии, исходный текст, чувствительные реквизиты | Анализировать **только через шлюз**, не иметь прямой доступ к хранилищу | Доверенный Windows-контур |
| B. Нормативный слой | Актуальные НПА/НТД, действовавшие редакции, области применения, даты, правила и их источники | Искать изменения, формировать актуализацию и новую версию требований через проверяемый интерфейс | Внутри коробки |
| C. Формы и табличная модель | Структура ИД, виды документов, обязательные поля, шаблоны, взаимосвязи | Заполнять согласованный формат, искать противоречия с заданными правилами | Внутри коробки |
| D. Словарь псевдонимов | Закрытая таблица `ИП Иванов ⇄ ИП 1849` с устойчивыми локальными ID | Видеть только псевдоним, не исходное имя; отвечать на вопросы с использованием псевдонимов | Только локально, включая обратную подстановку |
| E. Контроль полноты | Учёт всех файлов/страниц/листов/связей/версий, результаты сверок и неразобранные участки | Предлагать повторный проход и исправления, но не объявлять непроверенное «полным» | Локальная проверка + агрегированные показатели |
| F. Промежуточная версия | Структурированные сведения, формы и черновики, правки ИИ, замечания и история диалога | **Изменять рабочую промежуточную версию** через проверяемые операции шлюза | Windows-контур; на GPUgo — лишь разрешённый контекст |
| G. Выходной комплект | Документы, реестры, приложения и журнал контрольных операций | Подготовить комплект к финальной проверке; не подписывать за человека | ПТО получает уже подготовленный финальный набор |

## Пользовательский процесс A0

1. **Загрузка.** Сотрудник подаёт весь исходный комплект в защищённый аппендикс одной операцией; затем в общей таблице **для каждого файла отдельно** выбирает предметный тип из справочника коробки. Тип управляет локальным профилем разбора и обезличивания, но не является разрешением на передачу данных. На этом этапе нигде вне коробки нельзя хранить исходные файлы как часть AI-workflow.
2. **Индекс охвата.** Система фиксирует каждый файл, страницу/лист, версию, тип, ошибки парсинга и процент охвата. Для OCR/нестандартных форматов нужны локальные способы обработки.
3. **Шлюз.** Локальный компонент подбирает необходимую для анализа техническую информацию, заменяет закрытые имена/реквизиты локальными псевдонимами и блокирует неразрешённые фрагменты. Важное требование — сохранить контекст и связи, без которых сравнение РД, сметы и актов теряет смысл.
4. **ИИ GPUGO.** Модель анализирует весь доступный через шлюз объём по частям с журналом охвата, извлекает структуру, выявляет несоответствия, предлагает исправления; при необходимости обращается к разрешённым правилам/редакциям из коробки.
5. **Промежуточная версия.** Возвращаемые изменения проходят шлюз и структурную валидацию; не стирают оригинал. Они применяются к рабочему состоянию коробки как версионные правки и сохраняются для следующих итераций.
6. **Автоперепроверка.** Детерминированные правила сравнивают данные и требуемые поля, регистрируют нерешённые проблемы, повторно инициируют AI-проходы в пределах согласованного режима. `coverage=100%` не эквивалентно `correctness=100%`.
7. **Диалог в процессе.** Инженер может на естественном языке спрашивать о промежуточной версии. Локальный шлюз подменяет ФИО, названия организаций, иные идентификаторы, а в ответе безопасно восстанавливает разрешённые обозначения; ИИ не получает обратный словарь.
8. **Комплект.** Формы и реестры заполняются из текущих данных по правилам коробки, формируется итоговый пакет, при невозможности проверки включается отчёт об ограничениях/исключениях.
9. **ПТО.** **Проверяет и утверждает только финальный пакет**, а не каждую автоматическую итерацию. При замечаниях запускается новый цикл исправлений, а не подмена уже утверждённого оригинала.

## НПА/НТД: отдельная функция

Нормативная база **внутри** коробки. ИИ получает обновления из разрешённых внешних источников, определяет изменения и готовит обновления правил/форм. На практике запись в нормативный реестр должна проходить автоматическую проверку реквизитов, юридического статуса, редакции, периода действия, территории и источника; **нельзя позволять LLM напрямую и без проверки переписывать старые правила**. Предыдущие версии сохраняются.

На старте Windows-приложение показывает **дату последнего успешного подтверждённого обновления** нормативной базы и предупреждает об устаревшем/неполном статусе; время последней попытки скачать изменения — отдельное поле. Если проверка не завершилась или нет права на источник, нельзя ложно показывать «всё актуально».

## Пример диалога

Оригинал только локально: `ИП Иванов`, объект `<наименование>`, договор `<реквизиты>`.

Локальный словарь: `ИП Иванов ⇄ ИП 1849` (стабильный псевдоним для конкретной организации/проекта; таблица соответствий не экспортируется).

Инженер спрашивает: «Почему в акте по работам ИП Иванова не сходится объём?»

Шлюз преобразует запрос, локально привязывает вопрос к конкретным данным из коробки, создаёт безопасный технический контекст с псевдонимом `ИП 1849`. Внешний AI отвечает, используя этот псевдоним и доступные сведения. После проверки ответа локальный компонент возвращает человеку разрешённые реальные реквизиты.

**Ограничение:** одно переименование ФИО не защищает чувствительную документацию. Редкие технические характеристики, коды объекта, номера оборудования, геометки и сочетания полей могут деанонимизировать проект; нужен комплексный анализ связей и конкретная политика пропуска для разных типов запросов.

## Ключевое различие текущего кода и цели

**Это изменение требований к архитектуре.** Существующий `construction_docs/gateway.py::safe_batch` пропускает лишь заранее определённые категории замечаний и числовые метрики; модель GPUGO **не получает содержимое РД** и не может выполнить описанный полный анализ. В коде **нет** полноценного словаря псевдонимов, context policy engine, оркестрации полного объёма, версионной записи AI-правок в рабочую модель и автоматического обновления НПА. Старый PoC остаётся узким инструментом проверки реестра; новую A0 нельзя выдавать за уже реализованную.

Доработку начать с F01 (структура первоначальной загрузки), затем F02 (местные сущности/словарь/контекст и покрытие), F04 (новый двусторонний шлюз и AI-контракты), F03 (проверки и итерации), F07 (нормативная версия), F06 (генерация финального комплекта).
